# Changelog

## Overview

This document records the release history of the `ghcr.io/younsl/backstage` image so operators can tell what changed between two tags before rolling an upgrade. Use it to decide whether a tag carries a Backstage base upgrade, a plugin or dependency change, or only a rebuild, and to trace when a behavior first appeared in the deployed image.

The container registry keeps the tags but not the reasons behind them, and the Backstage upstream release notes cover only the base version, not the in-house plugins and configuration in this repository. This file is the only place both are written down together.

Headings are image tags, not Backstage versions. A rebuild at the same Backstage version increments the suffix (`1.53.0-1` to `1.53.0-2`), so the suffix is part of the release identity. Bumping `org.opencontainers.image.version` in the `Dockerfile` is what publishes a tag.

Tags released before this file existed (`1.51.0-1` through `1.53.0-3`) are not recorded here.

## 1.54.6-3

Released 2026-09-03. Built on Backstage [v1.54.6](https://github.com/backstage/backstage/releases/tag/v1.54.6) as the base version, the same base as `1.54.6-1`, so this tag differs only by the changes below.

- Slack MR Bot takes several merge requests at once, because review requests here are sent as a batch and one message per merge request buries the rest. `/mr` now opens a modal with five optional URL fields, one merge request per field, and submitting it comes back with one editable field per merge request holding its title. A field takes a pasted URL without the author having to type past a newline, and a field holding several URLs at once is still split correctly. `/mr <url> [<url> ...]` skips the URL step and goes straight to the titles. Empty fields are ignored and duplicate URLs are dropped rather than posted twice.
- Each title line ends with the diff stats GitLab shows on the Changes tab, `(+640 -4)`, appended after whatever the author typed rather than being part of the editable text, since the size of a change is a fact about the merge request and not a matter of wording. The numbers come from a GraphQL query (`project.mergeRequest.diffStatsSummary`), which is also where the title and web URL now come from, so one request per merge request covers all three. The REST merge request object carries no diff stats; when GraphQL is rejected — an older instance, or a token it does not accept — the plugin falls back to REST for the title and posts that line without stats.
- Lookups run in parallel after the modal is already on screen, so the modal no longer has to open within the merge request lookup. A failed lookup leaves its own field empty with the reason in the hint instead of failing the batch, so one unreachable project does not block a review request for four others, and fields left empty are skipped when posting. The earlier build resolved the merge request before opening the modal under a 2s cap, which does not survive a batch of five.
- Extra lines typed under a title are posted verbatim beneath that line, which is how a merge request carries a note about an upstream issue.
- Two URLs pasted with no separator between them are now split at each `http(s)://` rather than silently resolving to the first merge request number found in the combined string, and a URL with trailing junk is rejected outright: the merge request path is anchored to the end of the URL. Before this, `/mr <url1><url2>` posted one line and dropped the second merge request without saying so.

## 1.54.6-2

Released 2026-09-03. Built on Backstage [v1.54.6](https://github.com/backstage/backstage/releases/tag/v1.54.6) as the base version, the same base as `1.54.6-1`, so this tag differs only by the changes below.

- Slack MR Bot added as a backend-only plugin. Review requests in this team are posted by hand in Slack, and the moment an author wants review is rarely the moment the merge request was opened, so a repository webhook posts at the wrong time and a GitLab-specific Slack app cannot follow a project that later moves to GitHub. The plugin takes the request from the person instead: `/mr <merge request URL>` opens a modal with the merge request title pre-filled and editable, and posting sends the configured header line, the reference linked to the merge request (`!1728`), and a mention of whoever ran the command, into the channel the command was run in.
- The bot connects to Slack in Socket Mode, so Slack never calls into this instance. This Backstage is reachable only from inside the network, which rules out the slash command and `view_submission` request URLs an HTTP Slack app needs, and Socket Mode also removes the request signature verification and the unauthenticated endpoint that approach would have added. Several replicas are safe because Slack delivers each event to one connection.
- Merge request lookup is routed by URL host to a provider adapter, so a second forge is one more adapter rather than a second bot. GitLab ships in this tag; the URL path before `/-/merge_requests/<iid>` is taken as the project path, so nested groups resolve. The lookup runs before the modal opens and is capped at 2s, since Slack invalidates `trigger_id` after 3s, and a failed or slow lookup answers with an ephemeral message instead of an empty modal. A channel post that fails, which is what an uninvited bot looks like, is sent to the requester as a DM so the text is not lost.
- Configured under `slackMrBot` with `botToken` (`xoxb-`, scopes `commands` and `chat:write`), `appToken` (`xapp-`, scope `connections:write`), and optional `command` and `headerText`. Omitting `slackMrBot.providers` reuses the `integrations.gitlab` hosts and tokens, so no second GitLab credential is needed; reading a merge request needs `read_api` and project access, and GitLab answers `404` rather than `403` for a project the token cannot see. The plugin stays disabled while `slackMrBot.botToken` is unset, so an instance without the Slack app starts normally.
- `@slack/bolt` is a new runtime dependency, and `SLACK_MR_BOT_TOKEN` and `SLACK_MR_BOT_APP_TOKEN` are two new environment variables the deployment must supply before the bot can start.

## 1.54.6-1

Released 2026-08-31. Built on Backstage [v1.54.6](https://github.com/backstage/backstage/releases/tag/v1.54.6) as the base version, up from `1.54.4`.

- Base version bumped through `backstage-cli versions:bump`, which moved the backend to `@backstage/backend-defaults` `^0.17.8`, `@backstage/plugin-catalog-backend` `^3.9.1`, `@backstage/plugin-scaffolder-backend` `^4.1.0` and sibling patch releases, plus the matching frontend packages in the app. Two upstream patch releases and nothing more.
- In-house plugins accept a service principal on reads. Every self-service plugin resolved the caller with `allow: ['user']`, so an external static token declared under `backend.auth.externalAccess` got 401 from the list endpoints of GitLab Tokens, IAM Audit, OpenSearch, Capacity and S3 Log Extract and could only reach the routes that never checked identity at all. The auth helpers in those six backends (`gitlab-token-audit`, `iam-user-audit`, `opensearch-account`, `opensearch-viewer`, `opensearch-scaling`, `s3-log-extract`) now also accept a service principal on GET requests, with admin visibility so list endpoints return every row rather than the caller's own, and treat it as unauthenticated on any other method, before the dev-mode guest fallback can apply. A service token therefore cannot approve, review, mute, reserve, scan, delete or download anything through these routes, and the S3 archive download additionally fails its requester-or-admin check for it.
- The change exists for [backstage-mcp](../backstage-mcp/README.md), a separate Rust MCP server released as `ghcr.io/younsl/backstage-mcp` with its own chart, which exposes the catalog, search, TechDocs and every plugin page as read-only tools for kagent. The Helm values gain a `BACKSTAGE_MCP_TOKEN` environment variable and a `backend.auth.externalAccess` entry whose `accessRestrictions` confine the token to the fourteen plugins the tools read from, so the token cannot reach the scaffolder or the permission API. `app-config.yaml` carries the same block commented out, because an unset `${BACKSTAGE_MCP_TOKEN}` would stop the backend from booting locally.

## 1.54.4-2

Released 2026-08-28, rebuilt and overwritten in place later the same day. Built on Backstage [v1.54.4](https://github.com/backstage/backstage/releases/tag/v1.54.4) as the base version, the same base as `1.54.4-1`, so this tag differs only by the changes below. The rebuild folded in what was briefly published as `1.54.4-3`, which has been removed from the registry, so a pod already running the first `1.54.4-2` build must be restarted to pick up the last five items.

- OpenCost yearly overview loads in a fraction of the time. The page used to issue one `/costs` request per month, each returning every per-pod row for that month (thousands of rows on a busy cluster) only to be summed in the browser, plus one `/costs/controllers` request per month, and then waited for a live OpenCost API call before rendering anything. The yearly view now calls a new `/costs/monthly-totals` endpoint that returns a single SQL-aggregated row per month, fetches the controller list for the whole year in one request, and no longer blocks on the live call.
- The yearly table renders progressively. Months are requested newest first and each row appears as soon as its response lands, with a skeleton placeholder for months still in flight, so the current month is on screen before older months finish. Today's live cost is merged into the current month when the OpenCost API answers, and the footnote says so while it is still loading. Rows are ordered newest first to match.
- OpenCost schema bumped to version 3, which adds indexes on `opencost_daily_costs (pod_id)`, `opencost_monthly_summaries (pod_id)`, and `opencost_pods (cluster_id, controller)`, plus the `opencost_controller_filters` table below. Pod drill-down joined `daily_costs` by `pod_id` with no index on it, and the controller filter looked pods up by `controller` with none either, so both paths scanned the whole table for the cluster. The migration is guarded with `IF NOT EXISTS` and `hasTable` and runs once on startup.
- OpenCost gained controller filter presets. Month-end billing for a third party means pulling the same set of pods per cluster every month, and picking dozens of controllers by hand in the dropdown each time does not scale and is not reproducible. A preset is a named list of SQL LIKE patterns (`vendor-x-%`, `%-batch-worker`) matched against the controller name, created and edited from a dialog opened from the Preset dropdown on the OpenCost page and stored in the plugin database rather than in app-config, so no rebuild or redeploy is needed to change one. The editor previews the matched controllers, pod count, total and top pods for the selected cluster and month while typing. Selecting a preset restricts every view, the controller dropdown and every CSV export, is carried in the URL as `filter=<name>`, and can be limited to specific clusters. Backed by `GET/PUT/DELETE /filters`, `POST /filters/preview`, and a `filter` query parameter on the `/costs*` endpoints.
- Month view shows a Pod Breakdown table when a preset or controller filter is active: one row per matched pod with its monthly totals and days covered, and a CSV export. This is the per-cluster pod list the billing workflow needs and it did not exist before, since the month view only listed days and the pod list was one more click away per day.
- Every OpenCost CSV export now starts with a `Cluster` column. Exports from several clusters were indistinguishable once downloaded, and the filename was the only place the cluster survived. The value is the new `opencost.clusters[].alias` config key, which replaces `title`: the old key is no longer read, so operators must rename it in their app-config or the UI falls back to the bare cluster name.
- OpenCost controller dropdown no longer loads the full controller list. A cluster with many Jobs carries over 20,000 distinct controller names per year, and the dropdown fetched all of them on every page load, rendered every one as a DOM node, and re-filtered the whole list on each keystroke, which made the search unusable. `/costs/controllers` is now a server-side search: it takes a substring `q`, `kinds`, `excludeKinds` and `limit` (default 50, max 500), orders matches by total cost, and reports `truncated` when more rows matched than were returned. The dropdown queries only when opened, debounces typing by 300ms, renders at most 50 rows with their cost, and says when the search should be refined. Jobs are excluded by default behind an Include Jobs toggle, since their per-run names are what inflates the list and they are rarely what a filter targets. Controllers picked earlier stay selected even when they fall outside the current result page.
- The dropdown searches controller names only. Matching on the kind text (typing `Deployment` to list deployments) is gone, replaced by the Jobs toggle and the `kinds` parameter.
- Preset list shows who created each preset and when, and who last changed it. The backend records the calling Backstage user's entity ref on every save (schema version 4 adds `created_by` and `updated_by` to `opencost_controller_filters`), so a billing preset can be traced to its author without asking around. Presets saved before this build show the author as unknown.
- Preset editor preview no longer overflows. The Top Pods table grew with its rows and ran past the dashed preview border and under the Back and Save buttons. The preview panel is now capped in height and scrolls internally, with the pod table in its own scroll area and a sticky header.
- Preset filter is now a proper select matching Cluster and Year, with a Create row pinned at the bottom of the dropdown in place of the separate Manage button. The native select plus button pair looked out of place next to the other filters, and Manage landed on the preset list when the usual intent was to add one. Create opens the new-preset editor directly; the list with edit and delete is one Back click away. The Filters bar is ordered Cluster, Year, Controller, Preset.

## 1.54.0-3

Released 2026-08-21, rebuilt and overwritten in place on 2026-08-23. Built on Backstage [v1.54.0](https://github.com/backstage/backstage/releases/tag/v1.54.0) as the base version, the same base as `1.54.0-1`, so this tag differs only by the changes below.

- Forklift Coverage removed. Forklift now reports artifact repository adoption itself, so the scan in this image duplicated a number the source of truth already publishes, and a duplicate that lags a scan interval is worse than no duplicate at all. The `forklift-coverage` and `forklift-coverage-backend` plugins are deleted along with the sidebar entry, the `/forklift-coverage/*` route, and the `app.plugins.forkliftCoverage` flag. Read adoption in Forklift from now on.
- The sidebar label width override went with it. `sidebar-item-wide` existed only to keep "Forklift Coverage" from being clipped at the 110px cap that core-components puts on the label, and no other entry opted into it, so the class and its rule are gone rather than left as dead CSS for the next long name to rediscover.
- The plugin kept `forklift_coverage_settings` and `forklift_coverage_history` in its own `backstage_plugin_forklift-coverage` database. Removing the backend plugin stops it being read but does not drop it, so an operator upgrading to this rebuild keeps the wizard settings and the 90 day trend snapshots until they drop the database by hand. Nothing in the image will recreate it.
- Kafka Topic removed. Topic creation is already served by a ticket-based request flow owned by the team that operates the clusters, so a second self-service entry point split the same request across two channels and left neither with the full history. The plugin is dropped rather than kept as a read-only view, since a browser for topics nobody requests through here has no audience. The `kafka-topic` and `kafka-topic-backend` plugins are deleted along with the sidebar entry, the `/kafka-topic` route, the home quick link, the `app.plugins.kafkaTopic` flag, and the root `kafka` config block that carried the per-cluster broker lists and topic presets. The `kafkajs` dependency goes with them, so the image no longer ships a Kafka client at all.
- The plugin held its approval requests in a `kafka_topic_requests` table inside its own `backstage_plugin_kafka-topic` database. Removing the backend plugin stops it being read but does not drop it, so an operator upgrading to this tag keeps the request history until they drop it by hand. Nothing in the image will recreate it.

## 1.54.0-2

Released 2026-08-21. Built on Backstage [v1.54.0](https://github.com/backstage/backstage/releases/tag/v1.54.0) as the base version, the same base as `1.54.0-1`, so this tag differs only by the changes below.

- Forklift Coverage: the setup wizard carries a Stay quiet at full coverage toggle, which drops the scheduled Slack post when the scan left nothing to act on. Nothing to act on means at least one target project, every one of them applied, and no partial, not applied, or errored project, since a scan error hides a verdict rather than reporting a good one. A scan that found no target project at all still posts, because an empty target usually means the scope is wrong rather than the work being done. The toggle is off by default, so an existing instance keeps posting on every scheduled scan until someone turns it on.
- Forklift Coverage: Send now ignores the toggle. A report someone asked for is not noise, and once coverage is full it is the only way left to check that a webhook still reaches the channel, which a disabled button would take away. A skipped post is indistinguishable from a broken one when read from Slack, so the wizard states that the result currently on screen is the reason the next scheduled post will not arrive.
- Forklift Coverage: the toggle is stored per instance in a new nullable `webhook_skip_full_coverage` column, added to an existing settings table rather than recreated. While it is unset, `forkliftCoverage.webhook.skipWhenFullCoverage` in app-config decides, so the behavior can be pinned by config on an instance nobody has opened the wizard on.
- Forklift Coverage: the wizard's toggle rows lead with the switch instead of ending with it, so a column of toggles reads down one edge rather than making the eye track to the end of each label. The whole row stays one click target.

## 1.53.1-3

Released 2026-08-15. Built on Backstage [v1.53.1](https://github.com/backstage/backstage/releases/tag/v1.53.1) as the base version, the same base as `1.53.1-1`, so this tag differs only by the changes below.

- Platforms: a platform entry accepts `deprecated: true` in `app.platforms`, which marks it as heading for retirement in both the card and the grid view. The entry is still listed and still links out, so the marking greys the card out and fades it rather than colouring it: an owner retiring a service is a standing fact, not an alert competing with the production VPN notice on the same card. A headstone badge carries the word where there is room for it, the grid tile shows the icon and a Deprecated label under a desaturated logo, and hovering restores the card to near full contrast so it stays readable. Omitting the key leaves a platform supported.
- ArgoCD AppSets: an ApplicationSet deploying a chart whose `Chart.yaml` declares `deprecated: true` is marked with a headstone in the top right corner of its card, with the card greyed and dashed to match the Platforms treatment. The flag is read during the same `Chart.yaml` fetch that resolves the chart version, so it costs no extra request and is cached with it. Only a chart sourced from a git path can report this, since a chart pulled from a Helm repository is never read as a file.
- ArgoCD AppSets: hovering the headstone names the deprecated charts and says what the flag means, and the Chart Version Detail dialog states the same thing once at the top, marks the deprecated chart in the summary table, and marks the `deprecated: true` line in the file itself. That line is marked in grey rather than in the accent the reported version line carries, because two marks of equal weight would leave a reader unsure which value the dialog is about. A trailing comment on the line, which is where the note explaining the flag usually lives, does not stop it being found.

## 1.53.1-2

Released 2026-08-13, rebuilt over the 2026-08-12 build of the same tag. Built on Backstage [v1.53.1](https://github.com/backstage/backstage/releases/tag/v1.53.1) as the base version, the same base as `1.53.1-1`, so this tag differs only by the changes below.

- Forklift Coverage: the project table carries a Last Activity column between Status and Branch, because the verdict alone does not say which unwired project is worth the work. A repository pushed to this morning is something to schedule, the same verdict on one nobody has touched in half a year is a candidate for the exclude list. Ages read as `8h ago` up to a month and as months past that, with the exact timestamp on hover, and the column sorts oldest first to match the worst-first default. The project detail page states the same age with the full timestamp beside it. GitLab reports repository pushes and project record edits under one field, so the age can move without a commit.
- Forklift Coverage: the settings screen behind the gear is its own path, so it is linkable, survives a reload, and can be left with the browser's back button. An instance with no Forklift host configured now lands on that URL instead of swapping the body of the coverage page.
- Forklift Coverage: the scan summary records who asked for the scan, distinguishing a manual run by username from the cron schedule and from the backend's first-run seed scan. It is stored with the result, so a restart keeps the attribution, and only a scan that succeeds writes it, so a failure cannot reassign the result still on the page. Results stored before this show the age alone.
- Forklift Coverage: the scan summary reads as two icon-led facts, when-and-who and how long, rather than a sentence with separators.

- ArgoCD AppSets: each card shows the upstream chart version and the running app version, and an application badge opens a dialog with its health, chart, app version, synced revision, and running images, each image copyable in full and labelled by name and tag rather than by its whole registry path. A dialog rather than a tooltip because a tooltip dismisses before anything inside it can be clicked. The app version says whether it came from the image tag, which is what is running, or from the wrapper chart's declared appVersion, which is only used when no image matched and can be stale. Both come from the Application CRs the ApplicationSet owns, since `status.resources` on the ApplicationSet carries only names and sync status, so the service account now also needs list on `argoproj.io` `applications`. Without it the page still lists ApplicationSets, and says so: a banner names the missing permission rather than leaving every version field showing a dash that reads as missing data.
- ArgoCD AppSets: for an Application sourced from a chart directory in git, the chart version exists nowhere in the cluster, because `targetRevision` there is the git revision. The backend reads `Chart.yaml` from GitLab and reports the pinned dependency version, which is the version of the chart actually deployed rather than the wrapper's own. Reads are cached per repository, path and branch for an hour, keyed on the branch rather than the synced commit so a push does not invalidate every entry at once. Set `argocdApplicationSet.chartMetadata.enabled` to false to turn the reads off. An umbrella chart pulling several unrelated dependencies reports no version, since none of them describes it.
- ArgoCD AppSets: the app version is read from the image whose name matches the chart, the chart directory, the release name, or the wrapped dependency, and falls back to the only image when an Application has just one. An Application deploying several unrelated images reports the `Chart.yaml` appVersion, or nothing, rather than picking a component arbitrarily.
- ArgoCD AppSets: the chart version has a detail dialog showing the file it was read from, syntax highlighted and copyable, with the line the version came from marked and the path linking to that line in GitLab. Applications reading identical values are grouped into one entry.
- ArgoCD AppSets: the detail dialog opens with a row per chart giving its name, the version pinned today, the newest version upstream offers, and whether that is an upgrade. The upstream lookup reads the dependency's own repository, a Helm index over HTTP or a tag listing for an OCI registry, and runs only when the dialog opens: an index runs to tens of megabytes and has no business on a one-minute refresh. Prereleases are excluded from what counts as the newest version, and an index above 20MB is reported as unavailable rather than parsed, since parsing one would stall the backend.
- ArgoCD AppSets: a Check for updates button compares every chart against its upstream repository and marks the result on the page. The scan runs on the backend rather than in the browser, so its `x of y (n%)` progress and the minute-long cooldown that follows belong to the deployment: a reader watches a scan someone else started, and nobody can start another until the wait is over. It reads each distinct chart once, six at a time, so a chart deployed to five clusters is one lookup and charts sharing a repository share one index read.
- ArgoCD AppSets: what a scan finds is stored in the database, so the page marks what is upgradable on load without anyone pressing the button, results are the same for every reader, and a restarted backend does not forget. The cooldown is derived from the newest stored check, which is what makes it survive that restart. The Status column says how long ago each repository was read, so an answer served from the cache is not mistaken for a fresh one, with the exact time on hover. An Overview tile counts the ApplicationSets with a newer chart available and filters to them when clicked, and each marked card carries the same amber arrow, whose tooltip names the chart and both versions.
- ArgoCD AppSets: a version whose leading field runs past four digits is no longer read as a version, and where a repository publishes proper three-field versions the shorter ones are set aside. An OCI registry lists loose tags beside real chart versions, and karpenter's `20221219` was outranking every version it publishes.
- ArgoCD AppSets: a Helm index is cached per repository rather than per chart, so several charts from one repository cost one fetch and one parse instead of one each, and only the version and appVersion of each entry are kept, which is a fraction of what an index carries. A refresh revalidates with the entity tag, so an unchanged repository answers 304 with no body to read. Both are what make scanning every chart on a schedule affordable.
- ArgoCD AppSets: only repositories some ApplicationSet already depends on can be looked up, and the value used from then on is the one the lookup returned rather than the one the request carried, so the backend cannot be made to fetch an arbitrary address. That applies to the branch listing too. Reads are restricted to public HTTPS hosts, each redirect is checked rather than followed blindly, an OCI token realm must be on the registry's own host, GitLab requests are built against the configured API base rather than concatenated, and failures are logged rather than returned to the caller.
- ArgoCD AppSets: a query parameter repeated in the URL arrives as an array, which reached code expecting a string and failed there. Single values are now required, and rejected with a 400 rather than a 500.
- ArgoCD AppSets: the app version carries a warning when the Applications of one ApplicationSet are not all on the same version, listing which application is on which. A rollout that stopped partway looks exactly like an intended difference otherwise.
- ArgoCD AppSets: the target revision dialog shows the tip commit of the selected branch, with its author, message, short SHA linking to the commit, and how long ago it landed. Picking HEAD shows the default branch's commit. The branch listing already carried this, so it costs no extra request.
- ArgoCD AppSets: an empty list right after a backend restart no longer reads as an empty cluster. Until the backend reports its first fetch the page shows a live pending state and retries every three seconds, and the genuine empty state now names when the last fetch happened.
- ArgoCD AppSets: cards no longer print the generator types or repeat the `argocd` namespace, and the namespace filter is gone, since every ApplicationSet lives in one namespace.

## 1.53.1-1

Released 2026-08-09. Built on Backstage [v1.53.1](https://github.com/backstage/backstage/releases/tag/v1.53.1) as the base version. Rebuilt 2026-08-11 at the same tag, so an image pulled before that date does not carry the Forklift Coverage changes at the end of this list.

- Added the `platforms-backend` plugin, which records a visit each time someone opens a platform from the Platforms page and serves per-platform visitor stats. The Platforms page now shows a rank, a week-over-week trend, and daily and weekly visitor counts, inline on each card and in the hover tooltip in grid view. Tags on a card became buttons that toggle the page's tag filter. The plugin needs no app-config entry and is always on.
- Upgraded Backstage from 1.53.0 to 1.53.1. Errors in TypeScript configuration schema definitions no longer prevent the app from building or starting and are logged as warnings instead.
- Bumped `@backstage/backend-defaults` from 0.17.5 to 0.17.6 in `packages/backend`, `plugins/grafana-dashboard-map-backend`, and `plugins/openapi-registry-backend`.
- No create-app template changes in this release.
- Corrected the image tag in `values.yaml`, which still pointed at `1.52.1-2`.
- Forklift Coverage: every view has its own URL, so a pasted link opens the same view for the next reader. The list view keeps its status filter and search text in the query string, `/forklift-coverage` redirects to the list, and an unknown suffix redirects there too rather than dead-ending.
- Forklift Coverage: the setup page disables Send now while a scan is running and shows live counts beside the button, since a report sent mid-scan would list half-counted projects.
- Forklift Coverage: the timezone field became a searchable picker built from the browser's IANA zone list, with the current UTC offset in each label. A typo used to be rejected as an invalid cron expression, which named the wrong field.
- Forklift Coverage: the Slack summary title now links to the not applied filter instead of the bare plugin path, so the screen matches what the message is about. The line that appears past the 50 project cap carries that link too, and Slack link previews are turned off since every link already has a label.
